Introduccion

Que es el Sistema de Diseno Simon?

El Sistema de Diseno Simon (SD-SM) es la fuente unica de verdad visual y funcional para todos los productos de la plataforma Simon de rastreo y gestion vehicular.

⚙

Consistencia Visual

Garantiza que todas las pantallas, modulos y micro-frontends compartan la misma identidad visual, colores, tipografia y patrones de interaccion.

⚡

Desarrollo Acelerado

Los desarrolladores importan componentes pre-construidos y tokens CSS/TypeScript, eliminando la necesidad de reinventar estilos en cada feature.

🔎

Mantenimiento Centralizado

Un cambio en un token o componente del Design System se propaga automaticamente a toda la aplicacion, reduciendo errores y deuda tecnica.

🚀

Escalable con Micro-Frontends

Construido sobre Vite Module Federation y React 19, permite que multiples equipos trabajen en modulos independientes con la misma base de diseno.

Stack Tecnologico: React 19 + TypeScript + Vite 7 + Tailwind CSS 4 + MUI 7 + MapLibre GL. El sistema vive en src/lib/design-system/ y se importa via @/lib/design-system.
Arquitectura

Arquitectura del Sistema de Diseno

El SD-SM se construyo como una arquitectura por capas donde cada nivel depende solo de los niveles inferiores. Esta separacion permite que los tokens evolucionen sin romper componentes, y que los componentes se reutilicen sin acoplarse a features especificos.

Capas de la Arquitectura

5

MapPage, GeofencesPage, PanicPage • src/features/*/pages/
4
Features — Modulos de dominio
alerts, commands, geofences, map, panic • src/features/
3
Templates + Componentes — UI reutilizable
AppShell, MapLayout, Button, Modal, DataTable • src/lib/design-system/components/
2
Design Tokens — Variables de diseno
Colores, espaciado, tipografia, sombras, breakpoints • tokens.css + tokens.ts
1

Museo Sans, paleta Simon, lineamientos de marca, Figma "Sistema de diseno - SM"
Regla de dependencia: Cada capa solo importa de las capas inferiores. Un Button (capa 3) usa tokens.css (capa 2), pero nunca importa de features/ (capa 4). Una Page (capa 5) usa templates y componentes (capa 3), pero los componentes no saben en que pagina viven.

Estrategia CSS: Triple Capa

El sistema combina tres estrategias de CSS que se complementan entre si, cada una con un rol definido.

1

CSS Custom Properties

Los tokens viven como variables CSS nativas, accesibles en cualquier contexto (componentes, Tailwind, inline styles).

/* tokens.css */ --color-brand-400: #00F1C7; --spacing-4: 16px; --radius-md: 12px; /* Temas via selectores */ [data-theme="dark"] { --ds-color-surface: #000; }
2

BEM para Componentes

Cada componente del DS tiene CSS co-localizado con nomenclatura BEM y prefijo ds- para evitar colisiones.

/* Button.css */ .ds-btn { } .ds-btn--principal { } .ds-btn--sm { } .ds-btn__icon { } /* MapLayout.css */ .ds-map-layout { } .ds-map-layout__panel { } .ds-map-layout__overlay { }
3

Tailwind Utilities

Tailwind CSS v4 consume los tokens del DS como valores de tema. Se usa para layouts rapidos y en features.

/* tailwind.css @theme */ --color-primary: var(--color-brand-800); --color-surface: var(--ds-color-surface); <!-- En JSX --> <div class="grid grid-cols-2 gap-4 bg-surface rounded-lg">

Arquitectura Micro-Frontend

El sistema esta preparado para funcionar como modulo remoto dentro de una aplicacion host via Vite Module Federation. Esto permite que equipos independientes consuman el mismo Design System sin acoplar sus builds.

Exposicion del Modulo

vite.config.ts
federation({ name: "scada", filename: "remoteEntry.js", exposes: { "./ScadaModule": "./src/app/remote/ScadaModule.tsx", "./ScadaStyles": "./src/app/remote/ScadaStyles.ts", }, shared: ["react", "react-dom", "react-router-dom"], })

Principios de Integracion

  • ✓ CSS auto-inyectado: Los estilos se empaquetan en JS y se inyectan al DOM, sin que el host necesite importar CSS.
  • ✓ Temas del host: El host puede inyectar CSS variables custom que sobreescriben los tokens del DS.
  • ✓ React compartido: React, ReactDOM y React Router se comparten entre host y remoto para evitar duplicados.
  • ✓ ScadaProvider: Context provider que recibe configuracion del host (API URLs, tema, permisos).
  • ✓ Prefijo BEM ds-: Evita colisiones de CSS con los estilos del host.

Arquitectura de Temas

El sistema de temas opera en tres niveles, desde los tokens base hasta la personalizacion en runtime por parte del host.

Nivel 1
Tokens Base
--color-brand-400: #00F1C7 — Valores absolutos definidos en Figma.
Nivel 2
Alias Semanticos
--ds-color-surface: var(--color-white) — Mapeo contextual que cambia entre light/dark.
Nivel 3
Runtime Override
buildScadaThemeCssVars() — El host inyecta CSS vars custom via style={themeVars} en runtime.

Decisiones Arquitectonicas Clave

Tokens duales: CSS + TypeScript

Cada token existe en CSS (para estilos) y en TypeScript (para logica, charts, inline styles). Ambos se sincronizan manualmente desde Figma, garantizando paridad.

BEM con prefijo ds-

Todos los componentes del DS usan nomenclatura BEM con prefijo ds- (ej: .ds-btn--principal). Esto aísla los estilos del DS de los del host y de Tailwind.

CSS co-localizado

Cada componente tiene su archivo CSS junto al TSX (Button.tsx + Button.css). Facilita encontrar, mantener y eliminar estilos sin efectos secundarios.

Barrel exports tipados

Un unico index.ts exporta todos los componentes y sus tipos. Los features importan con import { Button } from '@/lib/design-system' sin conocer la estructura interna.

Templates como contratos

AppShell, MapLayout, FormLayout y TableLayout definen slots (sidebar, navbar, cards, footer). Los features solo proveen contenido; el layout lo resuelve el template.

Temas sin JavaScript

El cambio light/dark se resuelve 100% en CSS con selectores [data-theme] y .ds-theme-*. No hay re-renders de React al cambiar de tema.

Metodologia

Arquitectura Atomic Design

El sistema sigue la metodologia Atomic Design de Brad Frost, organizando los componentes en cinco niveles jerarquicos de complejidad creciente. Cada nivel se construye a partir del anterior.

1

Atoms

Elementos UI basicos e indivisibles. Son los bloques de construccion fundamentales.

Button Input Badge Avatar Checkbox Switch Icon
2

Molecules

Combinaciones de atomos que forman unidades funcionales con un proposito claro.

Tooltip Tab FilterBar KpiCard VehicleCard ProfileCard
3

Organisms

Secciones complejas de UI que combinan moleculas y atomos en interfaces completas.

Modal NavBar Sidebar Select DataTable Calendar
4

Templates

Layouts de pagina que definen la estructura y distribucion del contenido.

AppShell MapLayout FormLayout TableLayout ModuleShell
5

Pages

Instancias concretas de templates con datos reales del dominio.

MapPage ReportsPage GeofencesPage CommandsPage AlarmsPage
Principio clave: Los niveles inferiores nunca deben depender de los superiores. Un Button (atomo) no importa un Modal (organismo). El flujo de dependencia es siempre de abajo hacia arriba.
Fundamentos

Design Tokens

Los Design Tokens son las variables fundamentales del sistema: valores atomicos de color, espaciado, tipografia, sombras y bordes. Son la "fuente unica de verdad" que conecta diseno (Figma) con codigo.

Que son los Tokens?

Son decisiones de diseno convertidas en variables. En lugar de escribir #00F1C7 directamente, usamos var(--color-brand-400) en CSS o colors.brand[400] en TypeScript.

Esto permite que un cambio en la paleta de colores, por ejemplo, se propague a todos los componentes automaticamente, sin necesidad de buscar y reemplazar valores hardcodeados.

El sistema provee tokens en dos formatos: CSS Custom Properties (para estilos) y constantes TypeScript (para logica, charts, inline styles).

Categorias de Tokens

Colores 5 paletas × 11 tonos = 55 valores
Espaciado 18 escalas (base: 0.25rem)
Tipografia 9 escalas + 4 pesos + 3 breakpoints
Bordes 7 radios + 4 anchos
Sombras 5 niveles de elevacion
Breakpoints 4 puntos de quiebre responsivo

/* ── En CSS / Tailwind ── */ .mi-componente { background: var(--color-brand-400); padding: var(--spacing-4); border-radius: var(--radius-md); box-shadow: var(--shadow-sm); } /* ── En TypeScript ── */ import { colors, spacing, radius } from '@/lib/design-system/tokens'; const chartColor = colors.brand[400]; // "#00F1C7" const gap = spacing[4]; // "1rem"

Como Funciona

Automatico via tokens: La tipografia usa CSS Custom Properties que se redefinen en cada breakpoint con @media. Al usar clases como ds-h1 o variables como var(--text-h1-size), el tamano se ajusta sin codigo adicional.
Tailwind + componentes: Los templates (AppShell, MapLayout) manejan el layout responsivo internamente. El sidebar se colapsa, el panel se apila, y NavBottom aparece en mobile — todo via CSS, sin JavaScript condicional.
/* Los breakpoints son tokens CSS accesibles */ @media (min-width: var(--breakpoint-md)) { /* 48rem — Tablet */ } @media (min-width: var(--breakpoint-lg)) { /* 80rem — Desktop */ } /* En Tailwind CSS, los mismos breakpoints estan disponibles como prefijos */ <div class="grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3"> <!-- 1 col en mobile, 2 en tablet, 3 en desktop --> </div> /* En TypeScript, para logica programatica */ import { breakpoints } from '@/lib/design-system/tokens'; const isTablet = window.innerWidth >= parseInt(breakpoints.md); // 768

Guia Rapida

Como Usar el Sistema de Diseno

Tres pasos para integrar el Design System en cualquier feature o micro-frontend de Simon.

01

Importar Tokens

Los tokens CSS se cargan automaticamente via Tailwind. Para uso programatico, importa desde tokens.ts.

import { colors, spacing } from '@/lib/design-system/tokens';
02

Usar Componentes

Importa los componentes que necesites desde el barrel export del Design System.

import { Button, Input, Badge, Modal, DataTable } from '@/lib/design-system';
03

Aplicar Layout

Envuelve tu pagina en un template del sistema para obtener layout, navegacion y responsive gratis.

<AppShell> <TableLayout title="Reportes"> {content} </TableLayout> </AppShell>
Regla de oro: Nunca uses valores hardcodeados para colores, spacing o tipografia. Siempre usa tokens (var(--color-*) en CSS, colors.* en TS). Si el token no existe, propon agregarlo al sistema.
